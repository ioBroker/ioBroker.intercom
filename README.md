## English

This adapter runs an [Asterisk](https://www.asterisk.org/) PBX in a Docker container and configures it
completely from the ioBroker admin. Its focus is **WebRTC**: browsers and native apps (WebView + JsSIP) connect
with **SIP over WSS**, the media runs with **DTLS-SRTP and ICE** directly between the client and Asterisk.
Classic SIP phones and door intercoms (UDP) are supported as well.

### Features

- Subscribers (extensions) in a table of the admin: number, name, type (WebRTC/SIP), password, active
- Self-signed TLS certificate (RSA 2048, 10 years) generated by the adapter, SHA-256 fingerprint and QR code for
  certificate pinning in apps - or a certificate of ioBroker (e.g. Let's Encrypt from the ACME adapter)
- Docker container managed by the adapter (`@iobroker/plugin-docker`), or an Asterisk of your own
- Configuration changes are applied by an AMI reload, without dropping running calls
- Registration and call state of every subscriber in states
- Echo test on extension `600` and a WebRTC test page

### Requirements

- js-controller 7 or newer, admin 8 or newer, Node.js 22.19 or newer
- For the Docker mode: **Linux** with Docker. The container uses **host networking**
  (Docker Desktop on Windows/macOS does not support it).
- If ioBroker itself runs in a container, the configuration directory must be a path that exists on the
  Docker host as well.

### Getting started

1. Install the adapter and create an instance. On the first start it generates the AMI password, the
   certificate (for all IP addresses of the host) and the configuration directory, and restarts once.
2. A new instance already has two subscribers: `100` (WebRTC, password `0100`) for the browser and `101`
   (SIP, password `0101`) for a SIP app on a phone, e.g. Linphone. **Change these passwords** in the tab
   **Subscribers** - the adapter warns in the log as long as they are in use. Leave a password empty to get a
   random one.
3. The adapter writes the configuration and starts the container `iob_intercom_0_asterisk`
   (image `ubuntu:24.04`). On the first start Asterisk is installed with `apt` - **this takes a few minutes**.
   `info.connection` becomes `true` once the adapter is connected to Asterisk.
4. Open the test page `https://<ip>:8089/static/test.html` (button in the subscribers tab) and accept the
   certificate warning. **Without this step the browser refuses the WSS connection.**
5. Sign in as `100`, call `600` (echo test: you hear "hello world" and then yourself).
6. Register the phone app as `101` (server `<ip>`, UDP port 5060, realm `iobroker`) and call each other.

Ports on the host: TCP `8089` (HTTPS/WSS), UDP `10000-20000` (RTP), UDP `5060` only if SIP phones are configured.
AMI (`5038`) and plain HTTP (`8088`) only listen on `127.0.0.1`.

### Clients

| Setting       | Value                                      |
|---------------|--------------------------------------------|
| WebSocket URL | `wss://<host>:8089/ws` (see `info.wssUrl`) |
| SIP URI       | `sip:<extension>@<host>`                   |
| User / auth   | `<extension>`                              |
| Realm         | `iobroker`                                 |
| Media         | DTLS-SRTP, ICE, rtcp-mux (WebRTC default)  |

Apps should pin the certificate by the SHA-256 fingerprint shown in the settings (and in `info.certFingerprint`).
The certificate is **never regenerated automatically** - not even when IP addresses change (the adapter only
writes a warning to the log), because a new fingerprint breaks the pinning in all apps.

### Ring groups

A group number in the tab **Groups** rings several subscribers at once - e.g. the phone widgets and a FRITZ!Box,
so the door intercom calls one number and every phone in the house rings. The first one who answers takes the call,
the other phones stop ringing. Members that are not registered at the moment are left out; if none is registered,
the call ends at once. A group number must not be the number of a subscriber.

A FRITZ!Box (and with it its DECT phones) joins as a subscriber of type SIP: in the FRITZ!Box add a phone number of
"another provider" with the extension as number, user and authentication name, the address of Asterisk as registrar
and proxy and the transport UDP; disable "Insert area code for outgoing calls". Then let the FRITZ!Fon react to this
number.

### vis-2 widget "Phone"

The adapter brings a widget set for vis-2 (restart vis-2 after the installation if the set does not appear).
The widget **Phone** registers as a WebRTC subscriber and offers:

- audio and **video calls** (VP8/H.264, passed through by Asterisk - set the video codecs in the tab
  Asterisk; call `600` with video to see your own camera),
- a dialog that pops up for incoming calls (answer, answer with video, decline),
- the **picture of a door camera** (snapshot/MJPEG URL or a state with an image URL, e.g. of the cameras adapter)
  during calls without video, optionally also without a call,
- a **second camera** (e.g. the driveway): during a call a button in the picture switches between the video of the
  other party and the two cameras,
- **cameras of the frigate adapter** as picture source, selected from the list of the instance: as snapshots over
  ioBroker (works everywhere, also through the cloud) or as live MJPEG stream of its web extension (needs a web
  instance with HTTPS, because the phone page is HTTPS; otherwise the snapshots are used),
- an action button during a call, e.g. "Open door": sends DTMF tones and/or sets a state to `true`.

Settings: instance, extension and password of a WebRTC subscriber. The password is stored in the vis project,
so use a subscriber of its own for vis. Microphone and camera require that **vis is opened via HTTPS**, and the
browser must have accepted the certificate of Asterisk once (the widget shows a link).

vis-2 renders only the open view, so the phone is offline - and the door intercom reports a SIP error - while
another view is shown. Enable **"Render always"** in the settings of the view with the phone (Options): it stays
registered in the background, and the dialog of an incoming call opens on every view. The widget shows this hint in
the editor as long as the option is off.

The own camera is **off by default**: the picture of the other party is shown, but the widget opens the camera
only when "Use own camera" is enabled. Then video call buttons and the camera button in a call appear.

### Tile "Phone" for the devices app

The same phone is available as a tile in the [devices](https://github.com/ioBroker/ioBroker.devices) app (add a
widget to a category, "Phone"), with the same settings as the vis-2 widget. A tile of 1×1, 2×½ or 2×1 shows
whether the phone is ready or who is calling (2×1 also the camera picture), a click opens the whole phone in a
dialog. A 2×2 tile carries the phone itself. As in vis-2, the phone is online while its category is shown.

Several widgets or tiles with the same extension on one page share one phone and one registration, and a call
opens one dialog. Both bundles also bring a **background service** (`PhoneService` for vis-2, `IntercomService`
for devices) that keeps the phones of all widgets of a project registered on every view or category and shows the
dialog of a call there - without "Render always". It runs as soon as vis-2 and devices support such services
(in preparation); until then the widgets behave as described above.

### Camera pictures (snapshot proxy)

Many cameras deliver a snapshot only with a password, an API key or a token - which a browser cannot send in an
`<img>` of vis. Enter such cameras in the tab **Cameras**: the adapter fetches the pictures (Basic and Digest
authentication, API key header, Bearer token, self-signed certificates) and writes them as data URL into
`intercom.0.cameras.<name>.image`. In the phone widget select this state under "Camera picture from state".
During a call (a subscriber rings or talks) the picture is updated fast (default every second), otherwise slowly
(default every 10 seconds, 0 = off). Errors are logged once and written to `cameras.<name>.error`.

UniFi Protect: create an API key in UniFi OS (Settings → Control Plane → Integrations) and use
`https://<console IP>/proxy/protect/integration/v1/cameras/<camera ID>/snapshot` with the authentication
"API key (UniFi Protect)". The camera ID is part of the address of the camera in Protect.

### Objects

| Object                                | Meaning                                            |
|---------------------------------------|----------------------------------------------------|
| `info.connection`                     | connected to Asterisk (AMI)                        |
| `info.asteriskVersion`                | version of Asterisk                                |
| `info.certFingerprint`                | SHA-256 fingerprint of the certificate             |
| `info.wssUrl`                         | WebSocket URL for the clients                      |
| `subscribers.<ext>.registered`        | at least one reachable contact                     |
| `subscribers.<ext>.contacts`          | number of registered contacts                      |
| `subscribers.<ext>.userAgent`         | user agent of the client                           |
| `subscribers.<ext>.state`             | `idle`, `ringing`, `inuse`, `unavailable`          |

### Messages (`sendTo`)

| Command            | Message         | Answer                                                  |
|--------------------|-----------------|---------------------------------------------------------|
| `generateCert`     | `{ certHosts }` | `{ native: { certPublic, certPrivate, certFingerprint, certHosts } }` |
| `getHostAddresses` | -               | `{ native: { certHosts: [...] } }`                      |
| `getSubscriberStatus` | `{ extension }` | `{ text, style, icon }` for the table of the subscribers |
| `reload`           | -               | `{ result: 'ok' }` or `{ error }`                       |

### Own extensions

The adapter never touches `pjsip_custom.conf` and `extensions_custom.conf` in the configuration directory.
They are included at the end of the generated files.

### Asterisk without the Docker mode

Disable "Run Asterisk in Docker" and start the same container yourself:

```yaml
services:
    asterisk:
        image: ubuntu:24.04
        entrypoint: ['/bin/bash', '/etc/asterisk/iobroker/start.sh']
        network_mode: host
        restart: unless-stopped
        volumes:
            - /opt/iobroker/iobroker-data/intercom.0/asterisk:/etc/asterisk/iobroker:ro
```

Any other Asterisk (20 or newer, with `res_srtp`, `res_http_websocket` and `res_pjsip_transport_websocket`) works
as well: mount the configuration directory to `/etc/asterisk/iobroker` and put
`#include iobroker/<name>.conf` into `http.conf`, `pjsip.conf`, `rtp.conf`, `extensions.conf`, `manager.conf`
and `modules.conf`.

### Security

- Passwords are stored encrypted in ioBroker. Asterisk only gets `md5_cred` hashes (`auth_type=md5`).
- Secrets in clear text only exist in `manager.conf` and `keys/asterisk.key` (both mode `0600`).
- No anonymous access, no guest endpoint, legacy channel drivers (`chan_sip`, `chan_iax2`, ...) are not loaded.
- All values that end up in the configuration files are sanitized (no line breaks, `[`, `;`, quotes).
- Asterisk runs as root inside the container, because it has to read the key files of the host (mode `0600`).

### Asterisk log in ioBroker

Asterisk writes its log to `<configDir>/logs/iobroker.log` (a writable volume of the container), the adapter
follows it and forwards every message to the ioBroker log: `ERROR` as error, `WARNING` as warn, `NOTICE` as info,
`VERBOSE`/`DEBUG` as debug. Tab **Asterisk** → "Asterisk log in ioBroker" selects how much Asterisk logs
(default: errors and warnings). Set the log level of the instance to debug to see the verbose messages.
"Log SIP messages" adds every SIP message - only for troubleshooting. More than 50 messages per second are
dropped (never errors) and counted in a warning.

### Troubleshooting

- **The test page does not open**: Asterisk is still being installed. Look at the container log
  (`docker logs iob_intercom_0_asterisk`).
- **Registration fails with code 1006 / WebSocket error**: the browser has not accepted the certificate yet,
  or the address is not in the certificate.
- **Call connects but no audio**: UDP `10000-20000` is blocked by a firewall, or the network of the clients is
  part of "Networks excluded from ICE".

### Development

```bash
npm run npm         # install the root, src-www (test page), src-widgets (vis-2) and src-devices (devices) dependencies
npm run build       # TypeScript -> build/, test page -> build/static, widgets -> widgets/intercom, tile -> admin/dm-widgets
npm run lint
npm test            # build + unit tests + package tests
npm run test:integration   # starts js-controller and the adapter (without Asterisk)
UPDATE_SNAPSHOTS=1 npm run test:unit   # accept intended changes of the generated configuration
```

The phone core (`SipPhone`, without UI) is in `src-www`, the phone UI and the registry of the running phones in
`src-shared`; `src-widgets` and `src-devices` only adapt them to vis-2 and to the devices app.

## Deutsch

Der Adapter betreibt eine [Asterisk](https://www.asterisk.org/)-Telefonanlage in einem Docker-Container und
konfiguriert sie vollständig über den ioBroker-Admin. Der Schwerpunkt liegt auf **WebRTC**: Browser und native
Apps (WebView + JsSIP) verbinden sich per **SIP over WSS**, die Medien laufen per **DTLS-SRTP und ICE** direkt
zwischen Client und Asterisk. Klassische SIP-Telefone und Türsprechanlagen (UDP) werden ebenfalls unterstützt.

### Funktionen

- Teilnehmer (Nebenstellen) in einer Tabelle im Admin: Nummer, Name, Typ (WebRTC/SIP), Passwort, aktiv
- Selbst signiertes TLS-Zertifikat (RSA 2048, 10 Jahre) vom Adapter erzeugt, SHA-256-Fingerprint und QR-Code für
  das Zertifikats-Pinning in Apps - oder ein Zertifikat von ioBroker (z. B. Let's Encrypt aus dem ACME-Adapter)
- Docker-Container wird vom Adapter verwaltet (`@iobroker/plugin-docker`), alternativ ein eigenes Asterisk
- Konfigurationsänderungen werden per AMI-Reload übernommen, laufende Gespräche bleiben bestehen
- Registrierung und Gesprächsstatus jedes Teilnehmers als States
- Echo-Test auf Nebenstelle `600` und eine WebRTC-Testseite

### Voraussetzungen

- js-controller 7 oder neuer, Admin 8 oder neuer, Node.js 22.19 oder neuer
- Für den Docker-Modus: **Linux** mit Docker. Der Container nutzt das **Host-Netzwerk**
  (Docker Desktop unter Windows/macOS unterstützt das nicht).
- Läuft ioBroker selbst in einem Container, muss das Konfigurationsverzeichnis ein Pfad sein, den es auch auf
  dem Docker-Host gibt.

### Inbetriebnahme

1. Adapter installieren und Instanz anlegen. Beim ersten Start erzeugt sie das AMI-Passwort, das Zertifikat
   (für alle IP-Adressen des Hosts) und das Konfigurationsverzeichnis und startet einmal neu.
2. Eine neue Instanz hat schon zwei Teilnehmer: `100` (WebRTC, Passwort `0100`) für den Browser und `101`
   (SIP, Passwort `0101`) für eine SIP-App auf dem Handy, z. B. Linphone. **Diese Passwörter ändern** im Reiter
   **Teilnehmer** - solange sie aktiv sind, warnt der Adapter im Log. Bleibt ein Passwort leer, wird ein
   zufälliges erzeugt.
3. Der Adapter schreibt die Konfiguration und startet den Container `iob_intercom_0_asterisk`
   (Image `ubuntu:24.04`). Beim ersten Start wird Asterisk per `apt` installiert - **das dauert einige Minuten**.
   `info.connection` wird `true`, sobald der Adapter mit Asterisk verbunden ist.
4. Testseite `https://<ip>:8089/static/test.html` öffnen (Button im Reiter Teilnehmer) und die
   Zertifikatswarnung bestätigen. **Ohne diesen Schritt lehnt der Browser die WSS-Verbindung ab.**
5. Als `100` anmelden, `600` anrufen (Echo-Test: erst „hello world“, dann die eigene Stimme).
6. Die Handy-App als `101` anmelden (Server `<ip>`, UDP-Port 5060, Realm `iobroker`) und sich gegenseitig
   anrufen. Die States unter `subscribers.*` folgen dem Verlauf.

Ports auf dem Host: TCP `8089` (HTTPS/WSS), UDP `10000-20000` (RTP), UDP `5060` nur, wenn SIP-Telefone
konfiguriert sind. AMI (`5038`) und unverschlüsseltes HTTP (`8088`) lauschen nur auf `127.0.0.1`.

### Clients

| Einstellung   | Wert                                         |
|---------------|----------------------------------------------|
| WebSocket-URL | `wss://<host>:8089/ws` (siehe `info.wssUrl`) |
| SIP-URI       | `sip:<nummer>@<host>`                        |
| Benutzer      | `<nummer>`                                   |
| Realm         | `iobroker`                                   |

Apps sollten das Zertifikat über den SHA-256-Fingerprint aus den Einstellungen (bzw. `info.certFingerprint`)
pinnen. Das Zertifikat wird **nie automatisch neu erzeugt** - auch nicht bei geänderten IP-Adressen (dann gibt es
nur eine Warnung im Log), weil ein neuer Fingerprint das Pinning in allen Apps bricht.

### Gruppen

Eine Gruppennummer im Reiter **Gruppen** lässt mehrere Teilnehmer gleichzeitig klingeln - z.B. die Telefon-Widgets
und eine FRITZ!Box, sodass die Türsprechanlage eine Nummer anruft und alle Telefone im Haus klingeln. Wer zuerst
abhebt, übernimmt das Gespräch, die anderen hören auf zu klingeln. Mitglieder, die gerade nicht angemeldet sind,
werden ausgelassen; ist keines angemeldet, endet der Anruf sofort. Eine Gruppennummer darf nicht die Nummer eines
Teilnehmers sein.

Eine FRITZ!Box (und damit ihre DECT-Telefone) wird als Teilnehmer vom Typ SIP eingebunden: In der FRITZ!Box eine
Rufnummer „Anderer Anbieter“ anlegen, mit der Nummer als Rufnummer, Benutzername und Authentifizierungsname, der
Adresse von Asterisk als Registrar und Proxy und dem Transportprotokoll UDP; „Ortsvorwahl für ausgehende Gespräche
einfügen“ ausschalten. Danach das FRITZ!Fon auf diese Rufnummer reagieren lassen.

### vis-2-Widget „Telefon“

Der Adapter bringt einen Widget-Satz für vis-2 mit (vis-2 nach der Installation neu starten, falls er nicht
erscheint). Das Widget **Telefon** meldet sich als WebRTC-Teilnehmer an und bietet:

- Audio- und **Videoanrufe** (VP8/H.264, von Asterisk durchgereicht - Videocodecs im Reiter Asterisk; mit Video
  die `600` anrufen, um die eigene Kamera zu sehen),
- einen Dialog, der bei Anrufen aufgeht (annehmen, mit Video annehmen, ablehnen),
- das **Bild einer Türkamera** (Snapshot-/MJPEG-URL oder Datenpunkt mit Bild-URL, z.B. vom cameras-Adapter) bei
  Gesprächen ohne Video, wahlweise auch ohne Anruf,
- eine **zweite Kamera** (z.B. die Einfahrt): Im Gespräch schaltet eine Taste im Bild zwischen dem Video der
  Gegenseite und den beiden Kameras um,
- **Kameras des frigate-Adapters** als Bildquelle, ausgewählt aus der Liste der Instanz: als Snapshots über
  ioBroker (funktioniert überall, auch über die Cloud) oder als Live-MJPEG-Stream seiner Web-Erweiterung (braucht
  eine Web-Instanz mit HTTPS, weil die Telefonseite HTTPS ist; sonst werden Snapshots verwendet),
- eine Aktionstaste im Gespräch, z.B. „Tür öffnen“: sendet DTMF-Töne und/oder setzt einen Datenpunkt auf `true`.

Einstellungen: Instanz, Nebenstelle und Passwort eines WebRTC-Teilnehmers. Das Passwort steht im vis-Projekt,
deshalb für vis einen eigenen Teilnehmer anlegen. Mikrofon und Kamera funktionieren nur, wenn **vis über HTTPS**
geöffnet wird, und der Browser muss das Zertifikat von Asterisk einmal akzeptiert haben (das Widget zeigt einen Link).

vis-2 rendert nur die geöffnete View: Solange eine andere View angezeigt wird, ist das Telefon offline - und die
Türsprechstelle meldet einen SIP-Fehler. Deshalb in den Einstellungen der View mit dem Telefon **„Immer rendern“**
aktivieren (Optionen): Dann bleibt es im Hintergrund angemeldet, und der Dialog eines eingehenden Anrufs öffnet sich
auf jeder View. Solange die Option aus ist, zeigt das Widget diesen Hinweis im Editor.

Die eigene Kamera ist **standardmäßig aus**: Das Bild der Gegenseite wird angezeigt, aber das Widget öffnet die
Kamera nur, wenn „Eigene Kamera benutzen“ eingeschaltet ist. Erst dann erscheinen die Videoanruf-Tasten und die
Kamerataste im Gespräch.

### Kachel „Telefon“ für die devices-App

Dasselbe Telefon gibt es als Kachel in der [devices](https://github.com/ioBroker/ioBroker.devices)-App (in einer
Kategorie ein Widget hinzufügen, „Telefon“), mit denselben Einstellungen wie das vis-2-Widget. Eine Kachel in
1×1, 2×½ oder 2×1 zeigt, ob das Telefon bereit ist oder wer anruft (2×1 auch das Kamerabild); ein Klick öffnet das
ganze Telefon in einem Dialog. Eine 2×2-Kachel trägt das Telefon selbst. Wie in vis-2 ist das Telefon online,
solange seine Kategorie angezeigt wird.

Mehrere Widgets oder Kacheln mit derselben Nebenstelle auf einer Seite teilen sich ein Telefon und eine
Registrierung, und ein Anruf öffnet einen Dialog. Beide Bundles bringen außerdem einen **Hintergrunddienst** mit
(`PhoneService` für vis-2, `IntercomService` für devices), der die Telefone aller Widgets eines Projekts auf jeder
View bzw. Kategorie angemeldet hält und dort den Dialog eines Anrufs zeigt - ohne „Immer rendern“. Er läuft, sobald
vis-2 und devices solche Dienste unterstützen (in Vorbereitung); bis dahin verhalten sich die Widgets wie oben
beschrieben.

### Kamerabilder (Snapshot-Proxy)

Viele Kameras liefern ein Standbild nur mit Passwort, API-Schlüssel oder Token - das kann ein Browser in einem
`<img>` von vis nicht mitschicken. Solche Kameras im Reiter **Kameras** eintragen: Der Adapter holt die Bilder
(Basic- und Digest-Anmeldung, API-Schlüssel, Bearer-Token, selbst signierte Zertifikate) und schreibt sie als
Data-URL nach `intercom.0.cameras.<name>.image`. Im Telefon-Widget diesen Datenpunkt unter „Kamerabild aus
Datenpunkt“ auswählen. Während eines Anrufs (ein Teilnehmer klingelt oder spricht) wird das Bild schnell
aktualisiert (Standard jede Sekunde), sonst langsam (Standard alle 10 Sekunden, 0 = aus). Fehler landen einmal im
Log und in `cameras.<name>.error`.

UniFi Protect: In UniFi OS einen API-Schlüssel anlegen (Einstellungen → Control Plane → Integrationen) und
`https://<Konsolen-IP>/proxy/protect/integration/v1/cameras/<Kamera-ID>/snapshot` mit der Anmeldung
„API-Schlüssel (UniFi Protect)“ verwenden. Die Kamera-ID steht in der Adresse der Kamera in Protect.

### Eigene Erweiterungen

`pjsip_custom.conf` und `extensions_custom.conf` im Konfigurationsverzeichnis überschreibt der Adapter nie.
Sie werden am Ende der erzeugten Dateien eingebunden.

### Asterisk ohne Docker-Modus

„Asterisk in Docker betreiben“ abschalten und den Container selbst starten, siehe das `docker-compose`-Beispiel
im englischen Teil. Jedes andere Asterisk ab Version 20 mit `res_srtp`, `res_http_websocket` und
`res_pjsip_transport_websocket` funktioniert ebenfalls: Konfigurationsverzeichnis nach `/etc/asterisk/iobroker`
mounten und in `http.conf`, `pjsip.conf`, `rtp.conf`, `extensions.conf`, `manager.conf` und `modules.conf`
jeweils `#include iobroker/<name>.conf` eintragen.

### Asterisk-Log in ioBroker

Asterisk schreibt sein Log nach `<configDir>/logs/iobroker.log`, der Adapter liest mit und gibt jede Meldung ins
ioBroker-Log weiter: `ERROR` als error, `WARNING` als warn, `NOTICE` als info, `VERBOSE`/`DEBUG` als debug. Im Reiter
**Asterisk** legt „Asterisk-Log in ioBroker“ fest, wie viel Asterisk protokolliert (Standard: Fehler und Warnungen).
Für die verbose-Meldungen den Log-Level der Instanz auf debug stellen. „SIP-Nachrichten protokollieren“ nimmt jede
SIP-Nachricht mit auf - nur zur Fehlersuche.

### Fehlersuche

- **Testseite öffnet nicht**: Asterisk wird noch installiert. Container-Log ansehen
  (`docker logs iob_intercom_0_asterisk`).
- **Registrierung schlägt fehl (Code 1006 / WebSocket-Fehler)**: Der Browser hat das Zertifikat noch nicht
  akzeptiert, oder die Adresse steht nicht im Zertifikat.
- **Verbindung steht, aber kein Ton**: UDP `10000-20000` wird von einer Firewall blockiert, oder das Netz der
  Clients steht unter „Von ICE ausgeschlossene Netze“.
